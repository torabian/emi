Testing entity relations against sqlite

Prior to this work, array_test.go, collection_test.go, one_test.go and nested_relations_test.go only checked the generated Go shape (gorm struct tags, schema.Parse) via reflect — none of them actually created a row. The only end-to-end create/update coverage lived in actions_postgres_test.go, gated behind //go:build integration and a real Postgres instance (make entity-db-up).

That Postgres-only requirement wasn’t incidental: uniqueId’s default value used to be Postgres’s own gen_random_uuid() column default, which sqlite and MySQL have no equivalent for. Along the way this repo already fixed that (uniqueId is now assigned by a generated BeforeCreate gorm hook, in Go, on every dialect — see go-entity-default-fields.go), but the checked-in example SDK under examples/emi-entity/sdk hadn’t been regenerated since, so it still carried the old gorm:"type:uuid;default:gen_random_uuid();unique" tag and no hook. It’s been regenerated (emi compile --path examples/emi-entity/entity.emi.yml) as part of this work so the fix actually takes effect, which is what makes the sqlite tests below possible without a live database at all.

New test file: actions_sqlite_test.go (no build tag — runs under a plain go test ./examples/emi-entity/sdk/...). Each test opens a fresh sqlite file inside t.TempDir(), AutoMigrates the tables it needs, and drives the generated Entity1EntityActions.Create / .Update the same way a real caller would.

All 8 tests pass; results below.

7. Array-inside-array — delete operation, 3 levels deep

Section titled “7. Array-inside-array — delete operation, 3 levels deep”

Test: TestSqlite_ArrayInsideArray_DeleteRemovesOnlySelectedItems

items.subItems.subSubItems — an array nested inside another array, 3 levels deep. Until this test, array/array? only supported replace/append; deleting specific rows by id meant sending a replace with everything except those rows, and a relation declared on an array item’s own fields (an array-inside-array included) was an explicit, documented limitation — persisted as a flat unit via Save(), with no way to say replace/append/delete on it at all. Both are now fixed:

  • delete is a fourth operation on emigo.Array/ArrayNullable (emigorm.ReconcileHasMany) — each entry only needs its uniqueId; every other field is ignored. Rows not named are left completely untouched.
  • array-inside-array now reconciles correctly at any nesting depth — the preprocessor gives a nested array the same Operation-wrapped, uniqueId-prepended dto shape a top-level one already had, and the generator (buildArrayItemFields) recurses into an array’s own nested array fields, generating the identical reconcile call one level down.

Seed payload — one top-level item, 5 subItems, two of them (sub-2, sub-3) each carrying their own subSubItems:

Delete payload — only sub-2 and sub-4’s uniqueId, nothing else:

Result: 3 subItems remain (sub-1, sub-3, sub-5); sub-2/sub-4 are hard-deleted (db.Unscoped() finds 0 rows), and sub-2’s own subSubItems row (leaf-deleted-with-sub-2) cascades away with it — no level-3 orphan left behind (emigorm.ReconcileHasMany’s "delete" branch reuses the same Select(clause.Associations).Delete(&existing) gorm already used for replace’s own orphan cleanup, which cascades through has-many children the same way, no DB-level ON DELETE CASCADE/sqlite FK pragma needed). sub-3 (never touched by the delete) still carries leaf-kept-on-sub-3 untouched. ✅ PASS

What changed to make #7 possible

Section titled “What changed to make #7 possible”
  • emigo/Array.go / ArrayNullable.go: a new "delete" operation (plus ArrayDelete/ArrayNullableDelete constructors) — matches existing rows by uniqueId alone and removes them, leaving everything else untouched.
  • emigorm/reconcile.go: ReconcileHasMany gained a "delete" branch.
  • lib/core/preprocess-entities.go: cloneEntityOptionalField now recurses into an array’s own nested array sub-fields (previously only shallowCloneFieldd), so a nested array gets the same Operation-wrapped, uniqueId-prepended dto shape a top-level one already had.
  • lib/golang/go-entity-actions.go: the array-field body-building logic used by walkUpdateFields was extracted into a recursive buildArrayItemFields, so an array’s own nested array fields reconcile via the same generated emigorm.ReconcileHasMany call, one level down, at any depth.
