Events

A module can declare an events: list — flat, unlike permissions:, since an event is a single fact (“a post got published”), not a tree. Each event has a key (its wire name, and the basis its generated Go identifier is derived from), an optional localized name/description, a payload, and permissions describing who’s allowed to know it happened.

payload is compiled through the exact same machinery an action’s in/out body uses (the Common struct builder): declare fields inline and they’re compiled into a real, typed struct; reference an existing dto by name via dto: instead; or leave payload out entirely, and the event’s payload type falls back to a plain interface{}. permissions is a list of with blocks — the outer list is OR’d together, and each entry’s with (a list of permission full keys) is AND’d, e.g. [{with: [A, B]}, {with: [C, D]}] means (A and B) or (C and D).

Three events, three different payload shapes:

  • postPublished declares payload fields inline, so they’re compiled into a dedicated PostPublishedEventPayload struct — the same way an action’s request body would be — complete with its own CLI flags helper and Cast...FromCli constructor.
  • commentAdded points dto: at CommentDto (the struct comment’s own dto declaration generates — GetClassName appends Dto to a dto’s name, so the reference has to spell out the generated name, not the bare name: field). Its payload type is a plain alias to that existing struct, not a new one.
  • postArchived declares no payload at all, so its payload type aliases straight to interface{}.

A few things to note about the output:

  • One exported var per event, not a single var wrapping the whole list — each named PascalCase with a trailing Event (e.g. postPublished → PostPublishedEvent). The name is derived from key by normalizing it to UpperCamelCase (not just capitalizing its first letter), so post_published or post-published would both generate the exact same PostPublishedEvent a bare postPublished does. Because two differently-spelled keys can collide once normalized this way, the compiler rejects the module outright if any two events would generate the same name — a postPublished next to a post_published fails to compile with an explicit error, rather than silently letting one shadow the other.
  • Right alongside every event var, a <EventName>Payload type is always declared — a real struct when the event compiled payload fields, a plain alias when it referenced a dto or declared no payload at all — so there’s always exactly one identifier to reach for regardless of how (or whether) an event typed its payload.
  • emigo.Event.Permissions stays [][]string at runtime, same as before with was introduced — with is only the yaml-level spelling of each AND’d set; the compiler flattens it down when rendering the literal.
  • emigo.Event itself also carries a Payload interface{} field, left nil in every generated var above (it’s metadata, not an event instance). Alongside every event var, a New<EventName>(payload <EventName>Payload) emigo.Event constructor is also generated — it copies the var and sets .Payload, so application code that fires an event calls e.g. blog.NewPostPublishedEvent(payload) instead of copying the var and setting .Payload by hand at every call site.
  • AllEventsList collects every var declared above into a single []emigo.Event, for anything that wants to walk the whole catalog at once (seeding a notification-settings table, for instance) — built by referencing each var rather than re-declaring separate literals, so it can never drift out of sync with them.

This example (and every claim the generated code above makes) is asserted against the real compiler output by TestEventsGenerate in lib/golang/go-events_test.go — if the generator’s output ever changes, that test fails first, before this page can go stale.
